# 操作系统第三课：线程（Thread）—— 为什么 Go 能开 100 万协程

上一课我们学了：

```text
进程(Process)
=
运行中的程序
```

例如：

```text
微信
Chrome
GoLand
MySQL
Redis
```

都是进程。

---

今天我们解决一个问题：

```text
既然有进程了

为什么还要线程？
```

这个问题非常重要。

因为：

```text
线程
↓
协程
↓
Go Runtime
↓
GMP
```

是一条完整知识链。

---

# 先看进程的问题

假设你写一个浏览器。

用户打开：

```text
百度
知乎
B站
```

---

如果只有进程：

```text
Chrome
    │
    ├─ 加载页面
    ├─ 下载图片
    ├─ 播放视频
    └─ 执行JS
```

---

全部串行执行。

---

问题：

```text
下载图片
卡住

整个浏览器
卡住
```

---

于是出现：

```text
Thread（线程）
```

---

# 什么是线程

一句话：

> 线程是 CPU 调度的最小单位

---

进程：

```text
一个工厂
```

---

线程：

```text
工厂里的工人
```

---

例如：

```text
Chrome进程
│
├─ Thread1
├─ Thread2
├─ Thread3
└─ Thread4
```

---

多个线程：

```text
共享资源
```

同时工作。

---

# 进程和线程的区别

## 进程拥有独立资源

例如：

```text
微信
```

有：

```text
独立内存
独立文件
独立地址空间
```

---

而：

```text
Chrome
```

无法直接访问微信内存。

---

这叫：

```text
进程隔离
```

---

# 线程共享资源

同一个进程：

```text
Thread1

Thread2

Thread3
```

共享：

```text
Heap
全局变量
打开文件
Socket
```

---

例如：

```go
var count int
```

---

多个线程都能访问。

---

因此出现：

```text
线程安全问题
```

---

# 线程为什么比进程轻

创建进程：

```text
创建PCB
创建地址空间
创建页表
加载程序
```

---

很重。

---

创建线程：

```text
共享已有资源

只创建栈
只创建TCB
```

---

轻很多。

---

# 什么是 TCB

上一课：

```text
PCB
Process Control Block
```

进程身份证。

---

线程也有：

```text
TCB
Thread Control Block
```

---

里面记录：

```text
线程ID

寄存器

栈地址

状态
```

---

# CPU 真正在调度什么

很多人误以为：

```text
CPU调度进程
```

其实现代操作系统：

```text
CPU调度线程
```

---

例如：

```text
Chrome进程

Thread1
Thread2
Thread3
```

---

CPU看到的是：

```text
Thread1

Thread2

Thread3
```

---

不是Chrome。

---

# 为什么线程切换昂贵

假设：

CPU正在执行：

```text
Thread A
```

---

执行到：

```text
i = 100
```

---

突然切换：

```text
Thread B
```

---

CPU必须保存：

```text
寄存器

程序计数器

栈指针
```

---

否则回来找不到现场。

---

这个过程：

```text
Context Switch
上下文切换
```

---

非常重要。

---

# 什么是寄存器

CPU内部有超高速存储。

例如：

```text
AX
BX
CX
DX
```

---

执行：

```go
a := 1
b := 2

c := a+b
```

可能：

```asm
MOV AX,1

MOV BX,2

ADD AX,BX
```

---

AX BX就是寄存器。

---

切换线程时：

```text
必须保存寄存器状态
```

---

否则程序直接错乱。

---

# 为什么线程多了性能反而下降

很多新人认为：

```text
线程越多越快
```

错。

---

假设：

```text
8核CPU
```

---

开：

```text
100万个线程
```

---

CPU只能同时执行：

```text
8个
```

---

剩下：

```text
999,992个
```

排队。

---

操作系统不停：

```text
保存现场

恢复现场

保存现场

恢复现场
```

---

时间都花在：

```text
Context Switch
```

上。

---

这叫：

```text
线程风暴
```

---

# 用户线程和内核线程

这是 Go Runtime 的前置知识。

---

# 内核线程

操作系统认识。

例如：

```text
pthread
```

---

Linux：

```c
pthread_create(...)
```

---

创建后：

```text
内核知道它
```

---

CPU直接调度。

---

# 用户线程

操作系统不知道。

---

例如：

```text
协程
```

---

完全在用户空间管理。

---

操作系统眼里：

```text
不存在
```

---

所以：

```text
切换极快
```

---

# 三种线程模型

这是面试经典。

---

## 第一种

N:1

```text
用户线程
 │
 ├─ G1
 ├─ G2
 ├─ G3
 └─ G4

    ↓

Kernel Thread
    T1
```

---

多个用户线程：

```text
共享一个内核线程
```

---

优点：

```text
切换快
```

---

缺点：

```text
一个阻塞

全部阻塞
```

---

非常垃圾。

---

# 第二种

1:1

```text
G1 -> T1

G2 -> T2

G3 -> T3
```

---

Java早期大量采用。

---

优点：

```text
简单
```

---

缺点：

```text
线程太贵
```

---

开10万线程：

```text
内存爆炸
```

---

# 第三种

M:N

终于来了。

```text
G1
G2
G3
G4
G5
G6

    ↓

T1
T2
T3
```

---

多个协程：

```text
映射
```

到少量线程。

---

优点：

```text
协程极轻

线程数量可控
```

---

这就是：

```text
Go Runtime
```

采用的方案。

---

# 为什么线程需要栈

例如：

```go
func A() {
    B()
}

func B() {
    C()
}

func C() {}
```

---

调用：

```text
A
 ↓
B
 ↓
C
```

---

必须记录：

```text
返回地址
局部变量
参数
```

---

所以：

```text
每个线程都有自己的栈
```

---

# Linux 默认线程栈多大

通常：

```text
8MB
```

---

例如：

```text
10万个线程
```

需要：

```text
800GB
```

---

直接炸。

---

# Go 协程为什么牛

Go协程初始栈：

早期：

```text
4KB
```

现代：

```text
2KB 左右起步
```

动态扩容。

---

例如：

```go
go func() {

}()
```

---

创建100万个。

理论内存：

```text
2KB × 100万

≈ 2GB
```

---

还能接受。

---

# 为什么 Java 开几万个线程就危险

假设：

```text
8MB
```

一个线程。

---

开：

```text
10000
```

---

需要：

```text
80GB
```

---

直接OOM。

---

# 回到 Go

现在你已经知道：

```go
go func() {}
```

绝不是：

```text
创建一个线程
```

---

而是：

```text
创建一个 Goroutine
```

---

Goroutine：

```text
用户线程
```

---

真正线程数量：

```text
很少
```

---

这就是：

```text
M:N模型
```

的威力。
