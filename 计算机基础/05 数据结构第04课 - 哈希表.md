# 第四课：哈希表（Hash Table）

这一节是整个数据结构里面最重要的一节之一。

因为你每天都在用：

```go
map[string]interface{}
map[int]string
map[uint64]*User
```

Redis 也大量依赖哈希表。

很多系统的性能优化，本质上都是在利用哈希表。

---

# 先思考一个问题

假设有 1000 万用户：

```text
张三
李四
王五
赵六
...
```

你要查：

```text
王五
```

---

如果用数组：

```go
users := []string{
    "张三",
    "李四",
    "王五",
}
```

查询：

```go
for _, u := range users {
    if u == "王五" {
        return
    }
}
```

过程：

```text
张三？
不是

李四？
不是

王五？
找到了
```

---

如果：

```text
1000万用户
```

呢？

最坏情况：

```text
查1000万次
```

复杂度：

```text
O(n)
```

---

# 人类是怎么解决的

想象一本新华字典。

你查：

```text
王
```

不会：

```text
第一页
第二页
第三页
...
```

翻。

而是：

```text
直接翻到 W
```

附近。

---

哈希表也是这样。

核心思想：

> 不查找，直接定位。

---

# 什么是哈希

例如：

```text
张三
```

通过一个函数：

```text
Hash("张三")
```

得到：

```text
12345
```

---

再比如：

```text
李四
```

得到：

```text
88888
```

---

这样：

```text
张三 -> 12345

李四 -> 88888

王五 -> 45678
```

---

于是：

```text
数组位置12345
存张三

数组位置88888
存李四

数组位置45678
存王五
```

---

查询：

```text
王五
```

直接：

```text
Hash("王五")
```

得到：

```text
45678
```

然后：

```text
直接访问45678位置
```

完成。

---

# 为什么这么快

数组查找：

```text
一个一个比
```

---

哈希表：

```text
直接算位置
```

所以：

```text
O(1)
```

---

# Go 的 map

例如：

```go
m := map[string]int{
    "Tom": 18,
    "Jack": 20,
}
```

查询：

```go
age := m["Tom"]
```

实际上：

Runtime 在干：

```text
Hash("Tom")
↓
得到桶位置
↓
直接访问
```

---

# 哈希冲突

这里来了最重要的问题。

---

假设：

```text
Hash("Tom")
=
5
```

---

又来了：

```text
Hash("Jack")
=
5
```

---

都要放：

```text
桶5
```

怎么办？

这叫：

```text
Hash Collision
哈希冲突
```

---

# 第一种方案：链表法

桶5：

```text
Tom
 ↓
Jack
 ↓
Bob
```

变成：

```text
bucket5

Tom -> Jack -> Bob
```

---

查：

```text
Bob
```

时：

```text
Tom?
不是

Jack?
不是

Bob?
找到
```

---

所以：

```text
冲突越多
性能越差
```

---

# 第二种方案：开放寻址法

例如：

```text
5被占
```

就去：

```text
6
```

---

6也被占：

```text
7
```

---

一直找空位。

Redis早期部分结构用过。

---

# 为什么不能让哈希完全不冲突

很多初学者会问：

> 哈希函数设计好一点不就行了？

不可能。

例如：

```text
100亿用户
```

---

桶只有：

```text
1000万
```

---

数学上必然：

```text
多个用户
落到同一个桶
```

---

这就是：

```text
鸽巢原理
```

以后学算法还会见到。

---

# Go Map 的底层

Go 并不是：

```text
数组 + 链表
```

那么简单。

---

Go 使用：

```text
Bucket
```

桶结构。

---

大概：

```text
Bucket

key1 value1
key2 value2
key3 value3
...
key8 value8
```

一个桶：

```text
最多8个元素
```

---

为什么是8？

因为CPU缓存友好。

---

# 为什么不用链表

还记得上一课吗？

链表：

```text
Cache Miss
```

严重。

---

Go作者发现：

```text
遍历8个连续元素
```

比：

```text
链表跳来跳去
```

快得多。

---

所以：

```text
Go Map
=
数组
+
Bucket
+
少量溢出桶
```

---

# 为什么 map 查询接近 O(1)

例如：

```go
age := m["Tom"]
```

Runtime：

```text
Hash("Tom")
↓
定位Bucket
↓
扫描最多8个元素
↓
找到
```

---

所以：

```text
接近 O(1)
```

---

# 为什么 map 是无序的

很多人第一次踩坑：

```go
for k := range m {
    fmt.Println(k)
}
```

结果：

```text
每次顺序不同
```

---

原因：

Go故意设计的。

运行时会随机化。

防止程序员依赖顺序。

---

所以：

```text
Map 永远不要认为有顺序
```

---

# 为什么并发读写 map 会 panic

经典错误：

```go
m := map[string]int{}

go func() {
    m["a"] = 1
}()

go func() {
    m["b"] = 2
}()
```

可能出现：

```text
fatal error:
concurrent map writes
```

---

为什么？

因为写入时可能：

```text
扩容
搬迁
修改桶
```

---

同时写：

```text
数据损坏
```

---

所以 Runtime 直接：

```text
panic
```

保护你。

---

# sync.Map

如果需要并发：

```go
var m sync.Map
```

---

内部：

```text
读写分离
原子操作
```

实现线程安全。

---

# Map 扩容

假设：

```text
8个桶
```

已经快满了。

---

Go会扩容：

```text
8
↓
16
↓
32
↓
64
```

---

# 为什么不能一次搬完

例如：

```text
1000万元素
```

---

如果一次搬：

```text
停顿几秒
```

用户直接超时。

---

所以 Go 采用：

```text
渐进式迁移
```

---

每次访问：

```text
顺便搬一点
```

---

最终：

```text
旧桶
↓
新桶
```

慢慢完成。

---

这和 Go GC 的思想非常像。

后面讲 Runtime 时你会看到。

---

# Redis 为什么快

核心原因之一：

Redis 大量使用：

```text
HashTable
```

---

查询：

```text
user:10001
```

流程：

```text
Hash
↓
Bucket
↓
找到
```

---

复杂度：

```text
O(1)
```

---

所以：

```text
百万级Key
```

查询仍然极快。
