# 操作系统第八课：锁（Lock）—— 为什么两个线程同时 `count++` 会出错？

这一课是 Go 程序员必须彻底掌握的一课。

因为以后你每天都会写：

```go
sync.Mutex
sync.RWMutex
sync.Once
atomic
```

如果不知道底层，你就只能凭经验写代码。

今天我们要理解：

> **锁到底是在保护什么？**

---

# 先看一个最简单的例子

假设有：

```go
var count int
```

两个 Goroutine：

```go
go func() {
    count++
}()

go func() {
    count++
}()
```

很多初学者觉得：

```text
count 原来是0

+1

+1

最后一定等于2
```

实际上：

```text
有可能：

1

也可能：

2
```

为什么？

---

# 先理解 count++ 到底干了什么

很多人以为：

```go
count++
```

是一条指令。

其实不是。

CPU 看见的是：

```text
读
↓

加1
↓

写回
```

也就是：

```assembly
LOAD count -> AX

ADD AX,1

STORE AX -> count
```

三步。

---

# 两个线程一起执行

假设：

```text
count = 0
```

线程 A：

```text
读取

count=0
```

---

线程 B：

也读取：

```text
count=0
```

---

然后：

线程 A：

```text
0+1

写回

count=1
```

---

线程 B：

也：

```text
0+1

写回

count=1
```

---

最终：

```text
1
```

不是：

```text
2
```

---

这就是：

```text
Race Condition

竞争条件
```

---

# 什么叫竞争

一句话：

> 多个线程同时修改同一份数据。

例如：

```go
map

slice

count

全局变量
```

都可能发生。

---

# 临界区（Critical Section）

这也是面试高频词。

例如：

```go
count++
```

这一段：

```text
读取

修改

写回
```

不能被别人打断。

这段代码就叫：

```text
Critical Section

临界区
```

---

# 锁的本质

很多人觉得：

```text
锁
=
一种神奇的东西
```

不是。

锁本质就是一句话：

> **一次只允许一个线程进入临界区。**

例如：

```text
线程A
↓

获得锁

↓

执行

↓

释放锁

↓

线程B才能进去
```

---

# Mutex（互斥锁）

Go：

```go
var mu sync.Mutex

mu.Lock()

count++

mu.Unlock()
```

现在：

线程 A：

```text
Lock
↓

成功
```

线程 B：

```text
Lock

↓

失败

↓

等待
```

直到：

```text
A Unlock
```

B 才继续。

---

# Lock 内部发生什么

假设：

锁内部只有：

```text
locked = false
```

---

线程 A：

看到：

```text
false
```

于是：

```text
改成 true
```

成功。

---

线程 B：

看到：

```text
true
```

只能：

```text
等待
```

---

所以：

锁其实也是：

```text
一个共享变量
```

---

# 那锁自己不会竞争吗？

这是很多人第一次学锁都会想到的问题。

例如：

两个线程：

同时：

```text
locked=false
```

都想：

```text
改成true
```

怎么办？

---

答案：

CPU 提供了：

```text
Atomic Instruction

原子指令
```

---

# 什么叫原子操作

一句话：

> CPU 保证不可分割。

例如：

```text
读取

修改

写回
```

CPU：

一次完成。

任何线程：

```text
不能插队
```

---

这就是：

```text
Atomic
```

---

# CAS（Compare And Swap）

这是现代锁最核心的技术。

一定要理解。

---

CAS：

三个参数：

```text
地址

旧值

新值
```

例如：

```text
CAS(
    count,
    0,
    1,
)
```

意思：

```text
如果count还是0

改成1

否则失败
```

---

例如：

线程 A：

```text
count=0

CAS成功
```

---

线程 B：

此时：

```text
count=1
```

CAS：

失败。

---

然后：

```text
重试
```

---

# Go atomic

例如：

```go
atomic.AddInt64(&count, 1)
```

底层：

不是：

```go
count++
```

而是：

```text
CPU CAS
```

循环。

---

# 自旋锁（Spin Lock）

Mutex：

失败：

```text
睡觉
```

等待。

---

Spin Lock：

失败：

```text
while(true){

    再试

}
```

不停：

```text
CAS

CAS

CAS
```

---

为什么？

因为：

睡觉：

```text
线程切换
```

代价很高。

---

如果：

锁很快释放。

那么：

```text
一直等
```

反而更快。

---

# 什么情况下适合自旋

例如：

锁：

只持有：

```text
10纳秒
```

---

线程切换：

```text
1000纳秒
```

---

那么：

```text
睡觉
```

明显亏。

---

所以：

现代 Mutex：

都会：

```text
先自旋几次

再睡觉
```

---

Go 的 Mutex 就是这样。

---

# Go Mutex 底层

很多人不知道：

Go 的 Mutex：

不是：

```text
直接睡
```

而是：

```text
CAS

↓

自旋

↓

失败

↓

进入等待队列

↓

futex

↓

睡眠
```

这里的 **futex（Fast Userspace Mutex）** 是 Linux 提供的一种机制：没有竞争时，锁几乎完全在用户态完成；只有竞争激烈时，才通过系统调用进入内核等待。这也是 Go 的 `sync.Mutex` 性能很高的重要原因。

---

# 读写锁（RWLock）

例如：

```text
100个人

读配置
```

没有问题。

---

如果：

Mutex：

```text
一个人读

999人等
```

太浪费。

---

RWLock：

允许：

```text
100个人一起读
```

---

但是：

写：

必须：

```text
独占
```

---

例如：

```go
rw.RLock()

读取

rw.RUnlock()
```

---

写：

```go
rw.Lock()

修改

rw.Unlock()
```

---

# 为什么写不能同时进行

假设：

线程 A：

```text
Name="Tom"
```

---

线程 B：

同时：

```text
Name="Jack"
```

---

最后：

```text
不知道是谁
```

写操作必须独占。

---

# 死锁（Dead Lock）

经典问题。

例如：

线程 A：

```text
拿到了：

Lock A
```

等待：

```text
Lock B
```

---

线程 B：

```text
拿到了：

Lock B
```

等待：

```text
Lock A
```

---

结果：

```text
A 等 B

B 等 A
```

永远等。

---

这就是：

```text
Dead Lock
```

---

# 活锁（Live Lock）

比死锁更隐蔽。

例如：

两个人在走廊相遇。

A：

```text
你先
```

B：

```text
你先
```

一起往左。

一起往右。

永远让路。

一直动。

但是：

```text
谁也过去不了
```

---

这叫：

```text
Live Lock
```

---

# 饥饿（Starvation）

例如：

一直：

```text
读锁
```

不断进来。

---

写线程：

永远：

```text
等
```

---

这叫：

```text
Starvation
```

现代读写锁通常会加入公平策略，避免写线程一直得不到执行机会。

# Go 中什么时候用 Mutex，什么时候用 atomic？

这是实际开发里最常见的问题。

**适合 `atomic`：**

```go
atomic.AddInt64(&count, 1)
atomic.LoadUint64(&state)
atomic.StorePointer(...)
```

特点：

- 修改的是一个简单值（整数、指针等）
- 操作非常简单
- 希望性能最高

**适合 `Mutex`：**

```go
mu.Lock()
user.Name = "Tom"
user.Age++
user.Score += 10
mu.Unlock()
```

特点：

- 要修改多个字段
- 要保证一组操作整体一致
- 临界区逻辑比较复杂

不要为了追求性能把所有东西都改成 `atomic`。很多复杂逻辑用 `Mutex` 更简单、更不容易出错。

# 课后思考（一定要想）

假设有下面这段代码：

```go
var count int64

func Add() {
    atomic.AddInt64(&count, 1)
}

func Reset() {
    count = 0
}
```

问题：

> 这段代码是线程安全的吗？

提示：

- `Add()` 使用了 `atomic`
- `Reset()` 没有使用 `atomic`

想一想为什么，这个问题涉及 **原子操作与数据竞争** 的边界，也是很多线上 Bug 的来源。
