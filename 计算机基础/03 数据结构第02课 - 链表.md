# 第二课：链表（Linked List）

今天这节课非常重要。

因为你会发现：

```text
数组查询快
链表插入快
```

这句话虽然对，但实际上会误导很多程序员。

等学完今天这节课，你会明白为什么：

```text
Redis越来越少用链表
Go标准库几乎不用链表
现代CPU更喜欢数组
```

---

# 先复习数组

数组内存：

```text
地址

1000 -> 10
1004 -> 20
1008 -> 30
1012 -> 40
```

特点：

```text
连续存储
```

查询：

```go
arr[2]
```

CPU直接计算：

```text
1000 + 2 * 4
```

找到：

```text
30
```

所以：

```text
查询 O(1)
```

---

# 数组的问题

假设：

```text
10
20
30
40
```

插入：

```text
25
```

需要：

```text
10
20
25
30
40
```

于是：

```text
30 搬家
40 搬家
```

数据越多：

```text
搬家越多
```

所以：

```text
插入 O(n)
```

---

# 链表诞生

有人想：

> 我能不能不要连续内存？

于是链表出现。

---

# 单链表结构

内存可能是：

```text
1000 -> 10
5000 -> 20
8000 -> 30
2000 -> 40
```

完全不连续。

怎么办？

每个节点记录：

```text
下一个节点地址
```

例如：

```text
┌───────┬───────┐
│ 10    │ 5000  │
└───────┴───────┘

┌───────┬───────┐
│ 20    │ 8000  │
└───────┴───────┘

┌───────┬───────┐
│ 30    │ 2000  │
└───────┴───────┘

┌───────┬───────┐
│ 40    │ nil   │
└───────┴───────┘
```

形成：

```text
10 → 20 → 30 → 40
```

---

# Go实现链表

```go
type Node struct {
    Value int
    Next  *Node
}
```

例如：

```go
n1 := &Node{Value: 10}
n2 := &Node{Value: 20}
n3 := &Node{Value: 30}

n1.Next = n2
n2.Next = n3
```

形成：

```text
10 -> 20 -> 30
```

---

# 查询为什么慢

找：

```text
30
```

必须：

```text
先找10
↓
找到20
↓
找到30
```

无法：

```go
list[2]
```

因为：

```text
不知道30在哪
```

所以：

```text
查询 O(n)
```

---

# 插入为什么快

原来：

```text
10 -> 20 -> 30
```

插入：

```text
25
```

变：

```text
10 -> 20 -> 25 -> 30
```

只需：

```text
20.Next = 25

25.Next = 30
```

完成。

没有搬家。

所以：

```text
插入 O(1)
```

---

# 删除为什么快

原来：

```text
10 -> 20 -> 30 -> 40
```

删除：

```text
30
```

直接：

```text
20.Next = 40
```

完成。

所以：

```text
删除 O(1)
```

---

# 经典误区

很多教程说：

```text
链表插入 O(1)
数组插入 O(n)

所以链表更快
```

这是错的。

---

# CPU缓存（重点）

现代CPU：

```text
3GHz
```

速度极快。

内存：

```text
几十纳秒
```

速度远慢。

因此CPU有：

```text
L1 Cache
L2 Cache
L3 Cache
```

---

# 数组的优势

数组连续：

```text
10 20 30 40 50
```

CPU读取：

```text
10
```

时会顺便把：

```text
20
30
40
50
```

一起加载。

这叫：

```text
Cache Line
```

缓存行。

---

遍历：

```go
for _, v := range arr {
}
```

速度极快。

因为：

```text
CPU已经提前加载
```

了。

---

# 链表的问题

链表：

```text
1000 -> 10

5000 -> 20

8000 -> 30

3000 -> 40
```

CPU读取：

```text
10
```

后不知道：

```text
20在哪
```

必须再次访问内存。

每次都：

```text
Cache Miss
```

缓存失效。

---

结果：

```text
理论 O(1)

实际非常慢
```

---

# 为什么Redis逐渐放弃链表

早期Redis：

```text
List
```

底层：

```text
LinkedList
```

链表。

后来发现：

```text
缓存命中率低
```

性能不好。

改成：

```text
QuickList
```

实际上：

```text
链表 + 数组
```

混合结构。

---

# 为什么Go标准库很少用链表

Go确实有：

```go
container/list
```

标准库。

但是你几乎见不到人用。

原因：

```text
CPU缓存不友好
```

现代情况下：

```text
slice
```

往往更快。

---

# 双向链表

单链表：

```text
10 -> 20 -> 30
```

只能往后。

---

双向链表：

```text
10 <-> 20 <-> 30
```

节点：

```go
type Node struct {
    Prev *Node
    Next *Node
    Value int
}
```

可以：

```text
前进
后退
```

---

# Go标准库list

```go
import "container/list"

l := list.New()

l.PushBack("A")
l.PushBack("B")
l.PushBack("C")
```

结构：

```text
A <-> B <-> C
```

底层就是：

```text
双向链表
```

# 面试题3

为什么Redis不用链表做Hash？

假设：

```text
1000万用户
```

查：

```text
user_8888888
```

链表：

```text
O(n)
```

Hash：

```text
O(1)
```

所以Redis大量使用：

```text
HashTable
```

# 今天最重要的结论

记住下面这张表：

| 数据结构 | 查询 | 插入 | 删除 |
|----------|--------|--------|--------|
| 数组 | O(1) | O(n) | O(n) |
| 链表 | O(n) | O(1) | O(1) |

但是：

> 这是算法复杂度，不代表真实运行速度。

现代CPU下：

```text
数组 > 链表
```

很多时候成立。
