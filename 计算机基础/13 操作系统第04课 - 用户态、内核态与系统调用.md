# 操作系统第四课：用户态、内核态、系统调用 —— 一切 IO 的起点

这一课非常重要。

如果说：

```text
线程
↓
协程
```

是 Go Runtime 的基础。

那么：

```text
用户态
↓
内核态
↓
系统调用
↓
IO模型
↓
epoll
↓
Go Netpoll
```

是一条完整链路。

很多人会写：

```go
f, _ := os.Open("test.txt")
```

但不知道背后发生了什么。

今天讲完，你就知道了。

---

# 为什么要有内核态

先问一个问题：

如果程序可以直接操作硬件，会怎样？

例如：

```go
for {
    formatDisk()
}
```

或者：

```go
for {
    writeMemory(0)
}
```

或者：

```go
disableNetwork()
}
```

---

那任何程序都可以：

```text
删除系统文件
修改内存
控制网卡
关闭CPU中断
```

整个系统瞬间崩溃。

---

所以操作系统设计了一道墙：

```text
用户程序
    ↓
用户态(User Mode)

=================

内核态(Kernel Mode)
    ↓
硬件
```

---

# 用户态是什么

你写的：

```go
main()
```

---

你写的：

```go
Gin
Fiber
Gorm
Redis Client
```

---

全部运行在：

```text
User Mode
```

用户态。

---

权限非常低。

---

例如：

你不能：

```text
直接读网卡

直接读磁盘

直接访问物理内存

直接操作CPU寄存器
```

---

否则系统会乱套。

---

# 内核态是什么

操作系统核心：

例如：

```text
Linux Kernel
```

---

拥有最高权限。

---

可以：

```text
管理CPU

管理内存

管理磁盘

管理网络

管理进程
```

---

所以：

```text
用户态
=
普通老百姓

内核态
=
皇帝
```

---

# 一个经典图

```text
┌─────────────────┐
│     用户态       │
│                 │
│ Go程序          │
│ MySQL           │
│ Redis           │
└───────┬─────────┘
        │
        │ System Call
        ▼
┌─────────────────┐
│     内核态       │
│                 │
│ Linux Kernel    │
└───────┬─────────┘
        │
        ▼
     Hardware
```

---

# 什么是系统调用

重点来了。

---

例如：

```go
f, _ := os.Open("a.txt")
```

---

你觉得：

```text
Go直接打开文件
```

吗？

不是。

---

实际上：

```text
Go程序
↓
系统调用
↓
Linux
↓
磁盘
```

---

真正打开文件的是：

```text
Linux内核
```

---

# 为什么必须系统调用

因为：

```text
磁盘
网卡
CPU
内存
```

属于内核管理。

---

用户程序没有权限。

---

只能请求：

```text
内核帮我干
```

---

这就是：

```text
System Call
```

系统调用。

---

# 常见系统调用

Linux里最经典的：

```c
open()
read()
write()
close()
```

---

例如：

```go
os.Open()
```

最终：

```text
open()
```

系统调用。

---

---

```go
file.Read()
```

最终：

```text
read()
```

系统调用。

---

---

```go
conn.Write()
```

最终：

```text
write()
```

系统调用。

---

# 系统调用为什么慢

重点。

---

用户态：

```text
User Mode
```

切换到：

```text
Kernel Mode
```

需要：

```text
保存现场

切换CPU状态

执行内核代码

恢复现场
```

---

这个过程叫：

```text
Mode Switch
```

模式切换。

---

有成本。

---

虽然：

```text
微秒级
```

---

但比普通函数调用：

```text
慢几十倍甚至上百倍
```

---

# 举个例子

普通函数：

```go
Add()
```

可能：

```text
几十纳秒
```

---

系统调用：

```go
os.Open()
```

可能：

```text
几百纳秒
~
几微秒
```

---

差距巨大。

---

# 为什么系统调用不能太多

例如：

```go
for {
    conn.Write([]byte("a"))
}
```

---

每次：

```text
write()
```

系统调用。

---

100万次：

```text
100万次用户态切换
```

---

性能直接废掉。

---

所以：

```go
bufio.NewWriter()
```

出现了。

---

批量写：

```text
用户态先缓存
↓
一次系统调用
```

---

性能暴涨。

---

# 什么是 Trap

CPU怎么知道：

```text
我要进入内核
```

？

---

实际上：

执行特殊指令。

例如：

```asm
syscall
```

或者：

```asm
int 0x80
```

---

CPU看到：

```text
syscall
```

立即：

```text
用户态
↓
内核态
```

---

这叫：

```text
Trap
```

陷入内核。

---

# 一次完整的 read()

例如：

```go
buf := make([]byte, 1024)

file.Read(buf)
```

---

发生：

```text
用户态
    │
    ▼

read()

    │
    ▼

系统调用

    │
    ▼

切换内核态

    │
    ▼

内核读取磁盘

    │
    ▼

拷贝数据

    │
    ▼

返回用户态
```

---

这条链路必须记住。

以后：

```text
网络IO
epoll
Netpoll
```

都一样。

---

# 为什么 CPU 不一直待在内核态

有人会想：

```text
既然内核这么强

一直内核态不就好了？
```

---

不行。

---

原因：

```text
安全
```

---

如果所有程序：

```text
Root权限
```

运行。

---

系统分分钟被搞死。

---

所以：

```text
默认用户态

需要时进入内核态
```

---

# 什么是中断

现在来了。

另一个重要概念。

---

例如：

```go
http.Get(...)
```

---

请求发出去。

---

CPU会一直等吗？

---

当然不会。

---

CPU继续干别的。

---

等网卡收到数据：

```text
网卡
↓
中断CPU
↓
告诉内核
↓
数据来了
```

---

这叫：

```text
Interrupt
```

中断。

---

后面讲 epoll 时会详细展开。

---

# 用户态和内核态切换的代价

记住：

切换不是免费的。

需要：

```text
保存寄存器

切换栈

切换权限级别

恢复现场
```

---

所以高性能服务器追求：

```text
减少系统调用
```

---

例如：

```text
Redis
Nginx
Kafka
Go Netpoll
```

都在干这件事。

---

# 为什么 Redis 快

一个重要原因：

减少：

```text
read()

write()
```

调用次数。

---

尽量：

```text
一次读取更多

一次发送更多
```

---

减少：

```text
用户态 ↔ 内核态
```

切换。

---

# Go Runtime 的关系

你写：

```go
http.ListenAndServe(...)
```

---

背后：

```text
socket()

bind()

listen()

accept()

read()

write()
```

全是系统调用。

---

Go Runtime：

```text
Goroutine
+
Netpoll
```

负责让这些系统调用尽量高效。
